# DataPatch 面试讲解

原四题Agent轨迹先看 [PUBLIC_PROJECT_GUIDE.md](PUBLIC_PROJECT_GUIDE.md)，八题成品与策略看 [PUBLIC_EIGHT_TASKS.md](PUBLIC_EIGHT_TASKS.md)，实际成绩单独看 [RESULTS.md](RESULTS.md)。本页保留历史实验，历史两题结果不代表后续四题结果。

DataPatch 是 AI 辅助开发的个人项目，重点是让数据修复产出实际补丁、执行证据与可复核结果。公开四题历史 Flash 首轮 3/4；四份已审阅成品随后独立验收 4/4。新商品定点执行 v4.2 仍失败，v4.3 在失败候选上加入显式项目业务契约继续修复后原 pytest 11/11。以下把自主执行、成品交付和配置辅助分开讲，不合并成自主四题 4/4。

实现入口：`evidence.py` 生成真实数据变化证据，`review.py` 完成预算内候选复核，`audit.py` 只读审计报告与源码归档，模块回归已通过，当前完整测试结果见 ACCEPTANCE.md。执行主线与阅读顺序见 [CODE_READING.md](CODE_READING.md)。

## 90 秒讲法

> DataPatch 接收 dbt/DuckDB 数据工程工单，让 DeepSeek 选择读代码、查数据、改 SQL 和运行 dbt，交付实际补丁、工具轨迹和独立验收结果。
>
> 执行器约束文件和只读 SQL，聚焦上下文检查依赖、重复键和孤儿关系。公开业务契约向执行器返回反例；模型停止后，最终构建与工作区外原测试共同决定通过。Flash 有发送前费用预算，网络错误不自动重试；有快照的任务还能展示真实数据变化。
>
> 固定公开四题首轮通过三题，商品失败保留。交付的SQL经审阅后扩到八道固定公开题，9次成品验收尝试保留一次依赖准备失败，修复依赖后八个不同题最终通过；这是成品覆盖。后来把产品归属与收入来源明确为项目契约，从失败 AI 候选继续修复，4 次 Flash 调用通过商品原测试 11/11。记录明确保存辅助来源；它证明配置辅助修复可执行，没有把成品成绩或同题开发包装成未知任务泛化。

个人贡献另接一句具体事实，例如：“初版由 AI 辅助完成，我实际审阅了执行与验收链路，随后修改了〔实际函数〕，用〔实际反例〕验证。”方括号在完成个人修改后填写，当前两项候选见 [CODE_READING.md](CODE_READING.md)。

## 3 分钟讲法

**0:00–0:35：从静默数据错误切入。**

一单多条明细、一单多笔支付，直接关联再汇总会放大金额。SQL 能运行，数字仍错。DataPatch 的任务包括关联粒度、退款覆盖与零分母、业务日界、账号归并、增量重放和客户净收入建模。

**0:35–1:15：解释 Agent 决策与执行器。**

`Agent.run()` 负责模型与工具往返；`Workspace` 执行文件读取、只读查询、模型写入和 dbt。定向上下文提供目标 SQL、有限上游和相关 schema；新建目标缺失时先选择公开输入，关系剖析检查重复键、NULL 和孤儿候选。它统计全输入，仍需按工单筛选并确定业务可信键。长时间只有探索、预算剩余 ≤6 次且尚无补丁时，进入预算收尾阶段，暂收只读工具，写入后恢复。

**1:15–1:55：展示三类证据。**

第一类是代码和执行：真实 Diff、dbt 结果与停止原因。第二类是数据影响：已记录快照的 schema、行数和有效键上的 added/removed/changed；公开记录缺少快照时直接标缺失。第三类是业务正确性：公开契约与结束后的独立 Oracle／上游原 pytest。候选复核只看公开材料，意见必须引用真实要求；少于 6 次调用的短修复跳过复核。显式项目契约经 `install_public_contracts()` 安装，文件哈希和初始候选哈希进入报告。

**1:55–2:30：用已完成实验讲实际取舍。**

展示 54 次冻结的合成重复实验，三个模式分别为 18/18、17/18、17/18，context 的一次 Windows 存储故障保留在分母。修订后的 R2b 六题功能回归 6/6，共 52 次模型调用、89 次工具调用、191,325 Tokens。模式对照与单次功能回归各自展示。

**2:30–3:00：用公开工程讲归属与契约。**

商品非 NULL 产品键仍有孤儿，单看输出覆盖全部产品会遗漏销售事实。已审阅成品明确有效直接产品优先、缺失时经唯一变体回退，再在新工程原测试 11/11；四份成品合计验收 4/4。通用关系剖析的 v4.2 仍为 7/11；随后显式声明收入使用 `line_total`、可信归属和事实保全，v4.3 从失败候选用四次 Flash 调用修复到 11/11，独立验收通过。说明同题配置辅助与自主泛化的区别，最后展示自己实际修改的 Diff 和验证。

## 九个关键追问

### 1. 这里为什么需要 Agent？

任务创建、工具执行和最终评分是确定过程。自适应部分是定位模型、选择数据探针、解释反馈、修改 SQL 并决定下一步。工单变化时，动作顺序与参数也会变化。项目用多类任务观察这些决策的完成情况与成本。

### 2. 数据变化页面能证明补丁正确吗？

它先说明影响：列变了什么、行数如何变化、哪些键新增或消失、共有键上哪些值变了。初始模型本身可能错误，正确修复也可能改变所有行，所以变化不直接转成通过或失败。业务契约与最终 Oracle 另行判定。

### 3. 候选复核是不是又增加一个模型或额外预算？

使用同一配置的 DeepSeek，新建公开任务与候选证据的消息上下文。`verified` 在 `max_steps≥6` 且有候选和预算时最多复核一次，计入相同调用与费用上限；四调用的 v4.3 短修复跳过复核。finding 要有可匹配的 `requirement_quote`。历史 v3.1 两题复核后补丁又改变，哈希标记能说明审阅对应哪个候选，不能视为最终版本获批。

### 4. 实验支持什么结论？

54 次合成小样本中，ReAct 通过最多；数据覆盖六类相同语义的新变体。R2 首次回归 5/6，组合修订后六题 6/6。历史公开 v1→v2 总 Tokens 减少 68.1%，两题成功率仍为零。公开四题 v4.1 首轮通过三题；v4.3 证明一个有明确项目契约的失败候选可在预算内修到 11/11。配置、起点和源码不同，不能把各版拼成统一无辅助成功率，也没有对照证明候选复核或关系剖析单独提高了成功率。

### 5. 怎样避免自己生成答案、自己评分？

任务目录包含原始数据、业务文档、模型和部分公开契约；Python Oracle 与测试用参考修复留在评估侧。模型结束后，再运行最终构建和独立逐行检查／原始上游 pytest。显式追加的项目契约标注 `project_configuration`，v4.3 另存契约与失败候选起点，不包装成未受辅助的原题运行。review 只使用公开工单和候选证据。

### 6. 怎样发现“构建成功但业务错误”？

按粒度、覆盖、值和重跑行为分别检查。关联金额放大用订单粒度与金额守恒定位；退款比率需要计算关系；窗口排名还要明确总体。项目也复现过旧表导致的评分假阳性，因此最终构建成功和 Oracle 通过是共同必要条件。

### 7. 运行、回放和环境边界是什么？

当前交付验证的是可信 SQL 工程的本机执行：模型使用有边界的文件、SQL 和 dbt 工具。运行保存 JSON、事件、补丁和证据，工作台可回放历史。后台任务仍在进程线程池中；回放不包含重启后自动恢复执行。Docker/Harbor 与生产接入按各自实际验证状态说明。

### 8. 离线审计与个人下一步是什么？

`audit.py` 已实现 `audit_report()`、`audit_reports()`，只读核对覆盖、run ID、最终构建判定、Token/费用、汇总和源码快照，模块回归已通过，当前完整测试结果见 ACCEPTANCE.md。它还检出了修订前历史报告的一条失败误标通过。个人候选修改仍有退款比例语义契约、负净收入 stress 变体两项，目前均未实现；完成后展示实际 Diff 和执行记录。

### 9. 成品 4/4、辅助修复 11/11，能写成 Agent 四题全过吗？

不能。成品 4/4 来自已审阅 SQL 在全新工程中的零模型调用验收；v4.1 自主首轮仍是 3/4。v4.3 以失败 AI 候选为起点，增加收入来源、产品归属与事实保全的显式项目契约后，模型实际修改补丁并通过商品原 pytest 11/11。它展示工程配置与有界修复闭环，不是新题盲测，也不证明所有同类项目都应采用该归属政策。回放提供来源字段和原始判定供复查。
