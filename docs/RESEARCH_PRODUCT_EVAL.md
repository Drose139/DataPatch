# 数据 Agent 产品与评测调研：对 DataPatch 有用的机制

调研日期：2026-10-25。以下只采用项目维护者的一手仓库、源码或官方文档；调研没有把这些项目安装为依赖，也没有据其宣传估计本项目效果。建议围绕现有 dbt 修复闭环收敛。

## 六个一手项目的实际启发

| 项目与一手来源 | 核实的机制 | DataPatch 可用的改进与面试价值 | 取舍 |
|---|---|---|---|
| [WrenAI](https://github.com/Canner/WrenAI)，[架构说明](https://github.com/Canner/WrenAI/blob/main/docs/core/reference/architecture.md) | 把业务语义、相关对象定位、值域探查、计划追踪、验证和执行作为可组合能力；提供 dry-plan／dry-run；上下文中有显式业务定义 | 在目标上下文里区分“表结构”和“业务粒度／口径”；将代码变更、构建结果、业务检查与数据变化放在同一证据链。面试可以具体解释为什么可执行 SQL 仍可能算错钱 | 借鉴可检查的语义与分阶段反馈；当前无需搬入完整 MDL、连接器或 BI 平台 |
| [DB-GPT](https://github.com/eosphoros-ai/DB-GPT)，[维护者 README](https://github.com/eosphoros-ai/DB-GPT/blob/main/README.md) | 数据连接、规划、SQL／代码工具、可复用领域 skills 与成果报告组成端到端数据助手 | 将输入工单和最终补丁、数据结果、交付说明连起来；沉淀一个可运行的数据工程场景比追加聊天功能更有展示价值 | 当前只处理可信 dbt 项目，暂不增加 Python 任意执行、多源接入或通用工作流编辑器 |
| [Vanna](https://github.com/vanna-ai/vanna)，[上下文策略实验](https://github.com/vanna-ai/vanna/blob/main/papers/ai-sql-accuracy-2023-08-17.md) | 按问题选取相关 schema 和历史 SQL 样例，而非一次放入所有材料；其旧实验也明确讨论测试集及人工判断 | 可把“定向 schema／依赖”与实际首轮输入 Tokens 连起来检查；若以后采用例子检索，来源和是否经过独立确认必须记录 | 旧文中的准确率不能移用到 DataPatch；主仓库已在 2026-03-29 归档，不建议新增核心运行依赖 |
| [Harbor](https://github.com/harbor-framework/harbor)，[运行评测文档](https://github.com/harbor-framework/docs/blob/main/guides/running-evaluations.mdx)，[CLI 源码](https://github.com/harbor-framework/harbor/blob/main/src/harbor/cli/jobs.py) | 任务环境、Agent、verifier 与 trial 配置分离；独立记录重复 attempts、异常重试、并发与产物；可以导出解析后的配置 | 明确一个 run 是一次尝试；初始状态、模型预算、终止原因和评分修订可追溯。把模型失败与环境故障分开解释 | 可以借鉴协议字段；本机适配结果继续标 native adapted，不借用 Harbor 名称暗示已经完成官方容器跑分 |
| [Inspect](https://github.com/UKGovernmentBEIS/inspect_ai)，[评分政策](https://inspect.aisi.org.uk/scoring-policy.html)，[重评分](https://inspect.aisi.org.uk/tasks)，[多次运行指标](https://inspect.aisi.org.uk/metrics.html) | 区分可评分的正确／错误、执行或评分异常、无法评分；能对已有日志换 scorer 重算；重复结果可采用不同聚合方式 | 为已有证据做一次离线评分审计，保留旧结果和修订原因；严格区分单次通过、至少一次通过、每题所有重复均通过。无需再花 API 调用验证统计脚本 | 不必迁移到 Inspect；本项目可保留总体交付率口径，同时附任务错误／基础设施错误的数量，明确分母与过滤政策 |
| [data-eng-bench](https://github.com/Snowflake-Labs/data-eng-bench) | 面向数据工程的 DuckDB／Snowflake dbt 任务，输入业务目标与环境，由任务 verifier 验证最终效果 | 保留外部原始二元 reward 和组件解释，能展示“12／13 个组件通过仍整题失败”的真实业务边界 | 两道已用于调试的公开题是开发案例；后续改进不能把它们称为未见保留集，也不能由局部组件分数推断整题成功 |

这些项目分别证明了不同产品设计可以成立；没有在统一任务、预算和环境上跑过对照，不能声称 DataPatch 优于它们。

## 对当前项目最有价值的三项产品改进

### 1. 交付“数据发生了什么变化”的证据

模型输出文字和 Diff 说明改了哪些代码，业务检查说明是否满足指定规则，但用户还需要直观看到：输出行数如何变化、字段是否新增／移除／变型、同一业务键下哪些记录新增、删除或变化。

这与 WrenAI 的可检查业务上下文、DB-GPT 的结果交付思路相符，也是 DataPatch 当前可以用少量改动完成的展示：在已有执行记录旁增加前后快照与差异。**差异是变化证据，不是正确性评分**；正确性仍由最终构建与独立验收决定。没有稳定业务键或快照不完整时，只展示可确认的数据，不给出猜测的全量增删改数量。

### 2. 把上下文选择变成可解释的取舍

现有 `context.py` 已有目标识别、上游依赖、相关 schema 与字符预算。下一步的价值是展示实际选择了什么、哪些内容被截断、首轮输入用量与结果是否符合预期，而不是立即接入向量库、长期记忆或知识图谱。

面试可用一个真实例子说明：全库可见不等于任务相关；定向上下文降低成本也不自动保证语义正确。Vanna 旧实验只能作为设计依据，收益由本项目自己的日志验证。

### 3. 保留阶段结果，避免把“流程结束”当作“交付正确”

当前 `status=completed`、`final_build.success`、`verification.passed` 已分开记录。界面与报告应继续区分：是否产生补丁、能否构建、可见契约是否满足、最终业务验收是否通过，以及何时因步数或环境错误停止。

这能直接解释首轮公开失败：退款题有补丁且能构建，仍有业务分层错误；客户指标题没有修改代码。无需为此再建新的多 Agent 框架。

## 现有结果呈现的具体缺口

本节只读审阅了 `evaluation.py`、已完成的 v2 smoke／公开开发重测 JSON 与源码快照。正式仍运行中的报告不据此推断最终成绩。

| 已有基础 | 仍需补齐的解释或核验 | 一轮内可完成的处理 |
|---|---|---|
| protocol、逐次 records、summary 都已保存 | 完成状态、计划次数、实际次数与重复索引是否完整，尚缺一份独立校验记录 | 对每份完成报告核对任务 × 模式 × 重复的笛卡尔积，查漏项与重复，不发模型请求 |
| 有源码 SHA 与 source.zip | 读者不易确认报告对应哪份归档；评分器修订与 Agent 策略版本也容易混淆 | 校验归档内源码摘要并单列评分修订；不要用当前源码摘要冒充历史快照 |
| 有业务验收与构建字段 | 旧评分曾可能接受正确旧表；需要证明最终成绩使用修订后的 AND 规则 | 在已有记录上核对并另存重评分，保留原 build／Oracle 与修改前后计数 |
| 有基础设施失败计数 | 当前 `status=failed` 总称不足以解释文件持久化、API、模型内容或评分异常的不同影响 | 在结果说明中列出实际错误类别、原始 Run ID 与分母处理，不静默删失败或换成重测成功 |
| 有重复一致性与 Wilson 区间 | 同一题多次尝试相关；简单逐次区间不能解释为未知任务泛化置信保证 | 同时展示每题三次的结果矩阵与全部成功率；保持描述性结论，不做未经设计的显著性宣称 |
| 有费用估算与平均耗时 | Token 减少、费用下降和耗时改善是三种不同结论；多机制一起改也不是单因素因果 | 同一报告列实际调用、Token、耗时与停止原因；跨版本只作描述性对比 |
| 自建合成与公开开发报告已分开 | v2 smoke 与 v1 多模式重复对照的实验目的、样本数不同 | 结果首页明确各自目的与版本，不拼成一个“总成功率” |

## 已做的一次零 API 只读核验

本次从两份已完成源码归档中按项目 `source_digest()` 的规则重新计算摘要：

- `release_v2_smoke_20261025_source.zip` 的 12 个 Python 源码文件，与该报告 `protocol.source_sha256` 一致。
- `public_native_v2_20261025_source.zip` 的源码摘要，与该报告两次 trial 所声明的摘要一致。
- 两份归档对应的代码摘要均为 `7fb8fb2152886b376b5b6a16f962c244eb1033228a2ec3f8f69d2a2d1949cde7`。

这核实了“报告声称的源码与归档一致”，没有替代任务数据、依赖版本、预算、运行证据或评分正确性的审计。

## 建议下一轮只做离线协议与证据审计

不用新增评测框架，也不用重复模型批次。以现有 JSON／JSONL、原始 verifier 与源码归档为输入，输出一个 `artifacts/audits/<name>.json` 和简短 Markdown：

1. **协议完整性。** 核对 planned／completed 次数、唯一 `(task_id, mode, repeat)`、任务白名单、模型及预算字段。运行中或预算提前停止的报告不得冒充完整对照。
2. **版本一致性。** 复算 source.zip 摘要；对应 dataset 锁、外部 commit 与 verifier 原始／适配摘要；记录评分规则版本，不覆盖旧原始产物。
3. **计数复核。** 从 model 事件 usage 复算 prompt／completion／total Tokens；核对模型调用和工具调用，包含交付门控等自动执行；按原单价重算估算费用并允许既有小数舍入。
4. **评分复核。** 每条“成功”必须有成功的最终 build 与通过的独立验收；公开题还要有实际 pytest 执行和原始 reward 证据。列出无法复核的记录，不能默认为通过。
5. **统计复核。** 从逐次记录独立重算每模式成功数、分母、耗时、成本、每题全部重复成功率；与现有 summary 做逐字段差异，输出修订记录而不隐式修改历史。
6. **展示抽查。** 选一条通过、一条模型业务失败、一条环境失败，确认 UI 标签、Diff、检查和原始记录相符；旧记录没有前后数据证据时明确显示缺失。

完成标准是没有未解释的协议或汇总差异，每个例外有 Run ID 与原因。它能形成可复核的面试材料，比再追加一个通用 orchestration 层更直接。
